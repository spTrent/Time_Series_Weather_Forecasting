# Weather Forecast — Прогноз температуры по городам России

Прогнозирование температуры воздуха на **7 дней вперёд** (почасовые данные, горизонт по суткам) для 6 российских городов с помощью Decision Tree, Random Forest и XGBoost.

Стратегия — **Direct**: отдельная модель на каждый горизонт (день 1,...,день 7). Каждая модель по признакам, известным в момент `t`, напрямую предсказывает температуру в `t + 24·day`, не заглядывая в промежуточные часы.

Данные можно брать из двух источников: исходный `have_fun.xlsx` **или** база PostgreSQL, наполненная из [Open-Meteo](https://open-meteo.com/). Переключение — параметром `source` в `get_df` (`xlsx` или `db`).

> **MAPE намеренно не используется:** температура в °C проходит через 0, деление на близкие к нулю значения делает MAPE неинформативным. Вместо неё — WAPE (взвешенная по объёму ошибка).

### Почему метрики такие

**Ошибка растёт с горизонтом (MAE 2.10 → 3.30, R² 0.95 → 0.88).** Причина — **падение автокорреляции признаков с таргетом по мере роста горизонта**. Самые сильные предикторы — свежая история температуры (`current_temp`, `lag_1/2/3`, скользящие за 3–24 ч, `lag_24`). Их связь с целевой температурой сильна на коротком горизонте и **затухает** на длинном: температура «сейчас» отлично объясняет температуру через 24 часа, но слабо — через 168 часов, где успевает смениться синоптическая обстановка.

- На **дне 1** модель опирается на персистентность и свежую динамику → низкий MAE, R² 0.95.
- На **дне 7** свежие признаки почти не коррелируют с целью, и модель откатывается к **сезонному сигналу** (`day_of_year_sin/cos`, `lag_8760`, `month`), который задаёт лишь климатическое среднее → остаточная ошибка выше.
- Рост MAE **замедляется** к дню 5–7 (2.10 → … → 3.30): резкие приросты в начале, малые в конце — как раз потому, что автокорреляция сначала быстро падает, а затем выходит на плато.

**Directional Accuracy, наоборот, растёт с горизонтом (67% → 71.6%).** На длинном горизонте вопрос «будет теплее или холоднее, чем сейчас» определяется сезонным трендом (весной теплеет, осенью холодает) — его угадать легко. На коротком горизонте направление тонет в почасовом шуме, поэтому угадывать труднее. Это тот же эффект автокорреляции, только с другой стороны.

## Данные

Признаки (почасовая гранулярность):

| Колонка | Смысл |
|---|---|
| `ds` | временная метка (локальное время города) |
| `city` | город |
| `temperature_2m` | температура на 2 м — **целевая переменная** |
| `relative_humidity_2m` | относительная влажность |
| `precipitation`, `rain`, `snowfall` | осадки, дождь, снегопад |
| `weathercode` | код погодного явления (WMO) |
| `wind_speed_10m` | скорость ветра на 10 м |
| `surface_pressure` | давление на поверхности |

Города: Москва, Санкт-Петербург, Благовещенск, Находка, Сочи, Геленджик.

**Важно:** метки `ds` хранятся в **локальном времени каждого города** (у дальневосточных — со сдвигом до +10 ч от Москвы). Докачка из API приводится к тому же локальному времени, чтобы состыковаться с историей.

### Два источника (`get_df`)

```python
df = get_df(source='xlsx')  # сырьё из have_fun.xlsx — требует полной очистки
df = get_df(source='db')    # чистые данные из PostgreSQL — готовы к фичам
```

`xlsx` содержит артефакты (битая кириллица, опечатки в городах, текстовые коды погоды) и проходит полный блок очистки. `db` содержит уже подчищенные данные Open-Meteo.

## База данных (PostgreSQL)

### Схема `weather_hourly`

Первичный ключ `(city, ds)` — гарантирует уникальность «город + час» и делает возможным upsert без дублей. Создаётся автоматически при первом старте контейнера из `init/01-schema.sql`.

### Настройка

`.env` в корне проекта (в `.gitignore`):

```dotenv
POSTGRES_DB=weather
POSTGRES_USER=weather
POSTGRES_PASSWORD=your_password
PGDB_PORT=5432
```

Поднять базу:

```bash
docker compose up -d
```

Том `weather_pgdata` хранит данные между перезапусками. Полный сброс (с потерей данных): `docker compose down -v`.

### Скрипты

Все скрипты запускаются **как модули из корня проекта**:

| Скрипт | Назначение |
|---|---|
| **`src/db.py`** | `get_engine()` — подключение из `.env`; `upsert_weather(df)` — заливка датафрейма в `weather_hourly` через staging-таблицу и `INSERT … ON CONFLICT (city, ds) DO NOTHING` (идемпотентно, без дублей). |
| **`src/scripts/init_db.py`** | Читает `data/weather_clean.csv` и заливает в БД (`to_sql`). Разовая загрузка исторических данных, подготовленных ноутбуком. |
| **`src/scripts/get_weather.py`** | Тянет почасовую историю **одного города** за период из Open-Meteo **Archive API**, приводит к схеме (в т.ч. `weather_code` → `weathercode`, локальное время) и делает upsert. Запуск интерактивный: спрашивает город и даты. |
| **`src/scripts/get_history_weather.py`** | **Полная перезаливка**: `TRUNCATE weather_hourly`, затем качает **все города** за диапазон дат батчами по годам (upsert). Для сборки датасета с нуля только из Open-Meteo. |

Собрать историческую часть из Excel, затем дополнить свежими данными из API.

```bash

```


```bash

```

## Гайд B — БД с нуля, только Open-Meteo

Самый чистый вариант: единый источник данных, без смешения с Excel.

```bash

python -m src.scripts.get_history_weather
#   Введите начало: 2013-01-01
```

Скрипт пройдёт по всем 6 городам, годовыми батчами скачает историю из Archive API и зальёт через upsert. Дальше в ноутбуке использовать `get_df('db')`.

## Пайплайн (`src/ts.ipynb`)

1. **Загрузка** — `get_df(source)`: Excel или БД.
2. **Очистка** (для `xlsx`): кириллица, нормализация городов, парсинг текстовых кодов погоды, заполнение пропусков, физические диапазоны, скользящий z-score (окно 24 ч).
3. **Выравнивание часовой сетки** — `asfreq('h')` по городам: вставка пропущенных часов + интерполяция/ffill.
4. **EDA** — гистограммы/boxplot, тренды, ADF-тест, ACF/PACF, спектр Фурье, вейвлет-скалограмма, STL-декомпозиция.
5. **Инжиниринг признаков** — лаги (1, 2, 3, 24, 8760 ч), циклическое кодирование времени (month/day_of_year/hour × sin/cos), разности, скользящие по температуре/осадкам/ветру/давлению, `current_temp` (температура в `t`), OneHotEncoder города.
6. **Разбивка** — Train ≤ 2023, Validation = 2024, Test ≥ 2025.
7. **Обучение** — Direct-модели на каждый горизонт, подбор гиперпараметров Optuna (seeded, воспроизводимо), сравнение с наивным бейзлайном (`current_temp`).
8. **Оценка** — MAE / WAPE / Directional Accuracy / R² на тесте.
9. **Сохранение** — лучшие модели (`Models/model_day_N_with_{source}.json`) + `feature_schema.joblib` (порядок колонок для API).
